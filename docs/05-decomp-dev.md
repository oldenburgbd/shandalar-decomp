# Publishing progress to a local decomp.dev

[decomp.dev](https://github.com/encounter/decomp.dev) is the decompilation community's progress
site. We run it **locally** to visualise this project's progress in the same shape the rest of
the scene uses.

**Live at <http://localhost:3000/mtg-re/shandalar>** once the server is running.

## Three local modifications were required

These are marked `LOCAL-ONLY (not upstream)` in the source. They are **not** upstream bugs;
they are consequences of running a GitHub-oriented service with no GitHub.

1. **`.cargo/config.toml` — `[build] target-dir = "C:/Users/bo1026/decomp-target"`**
   The GNU toolchain's `dlltool.exe` cannot handle the space in `RE Project`; it splits the path
   and fails to build `getrandom`, `windows-sys` and `parking_lot_core`. Moving the target
   directory out of the spaced path fixes it. Build then takes ~4 minutes.

2. **`crates/github/src/lib.rs` — GitHub auth downgraded from fatal to a warning.**
   `GitHubConfig.token` is a required `String`, and `crates/web/src/main.rs` does
   `.expect("Failed to create GitHub client")`. With a placeholder or empty token the process
   panics with exit 101 *before binding the port*. Making the initial `client.current().user()`
   check non-fatal lets the server boot. Everything database-backed then works; only GitHub sync
   is unavailable, which we do not use.

3. **`crates/local` — a new workspace member** providing `decomp-dev-local.exe` with
   `validate` / `selftest` / `import` subcommands, because there is no other way in (below).

`dev_mode: true` in `config.yml` makes local login a superuser with no GitHub involvement.

## There is no upload endpoint — this is the important part

decomp.dev is a GitHub bot. Its only ingestion path is:

> poll a repository's GitHub Actions workflow runs → download the artifact whose **name** matches
> `^(?P<version>[A-z0-9_.\-]+)[_-]report(?:[_-].*)?$` → unzip it → find a file whose **stem** is
> `report`, `<version>_report`, or `progress` → `Report::parse()` → `report.migrate()`

Confirmed by reading every route in `crates/web/src/handlers/mod.rs`:

- Nothing accepts a report body. The 50 MB body limit on `POST /manage/{owner}/{repo}` is for the
  hero image.
- `/api/github/webhook` needs a GitHub App plus an HMAC signature, and only *enqueues a job that
  then downloads artifacts from GitHub*.
- The `Import` subcommand in `crates/cli/src/main.rs` is **commented out**; `cmd/import.rs` does
  not exist.
- `/manage/new` makes three live GitHub calls and refuses a repo with no completed `push` workflow
  run carrying a report artifact — so it is unusable offline. (Platform `win32` *is* selectable.)

### Why not raw SQL

Because the storage is not a blob of JSON. `reports.data` is **zstd-compressed protobuf**; units
are stripped out into a content-addressed `report_units` table keyed by **BLAKE3 of the
uncompressed protobuf**, joined through `report_report_units(report_id, report_unit_id,
unit_index)`. Hand-writing SQL would mean reimplementing protobuf, zstd and BLAKE3.

`Database::insert_report` does all of it, and upserts the `projects` row itself
(`ON CONFLICT (id) DO NOTHING`), so a single call registers both project and report. That is what
`decomp-dev-local.exe import` wraps.

## Report format notes

Generated by `tools/progress/objdiff_report.py`. Verified against objdiff-core's real parser:

- **Schema version must be present and equal to `2`.** If `version` is absent, pbjson defaults it
  to `0`, which triggers `migrate_v0`, which then demands `measures` on every unit.
- **Addresses are JSON numbers or decimal strings — never hex.** `"0x10001000"` is *rejected*
  (`invalid digit found in string`). objdiff-core generates its JSON layer with `pbjson-build`,
  whose `NumberDeserialize<u64>` parses a string branch with plain `u64::from_str`. The
  `serialize_hex` / `deserialize_hex` helpers apply only to `LegacyReportItem`, the pre-protobuf
  v0 format. Our generator emits numbers (`--addr-format int`); `str` would match objdiff's own
  writer byte for byte, which we do not need.
- **snake_case is correct.** objdiff builds with `.preserve_proto_field_names()`; the
  deserializer also accepts camelCase aliases.

## Expect the project to be hidden from the index until 0.5%

`project_visibility()` returns `Hidden` below **0.5% matched code**, and
`handlers/project.rs` filters hidden projects off the `/` index. The project page itself says so
and works fine by direct URL. This is upstream behaviour and resolves itself once real progress
lands — do not work around it.
